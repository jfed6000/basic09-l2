basic09-l2: the parts

An overview of the l2basic09 system for NitrOS-9 Level 2 on the Wildbits, how its parts fit together, the address-space limits that shape it, and a comparison with how OS-9 Pascal runs programs larger than memory.    |  (the editor)  | <---------------- |  (runtime)   | <--------------- | (compiler) |

           |                               |        |                         |

   +-------v--------+                      |        +-------->  l2b09ovl  <---+
   |  l2b09help     |<-- basic09-l2.hlp    |                   (overlay)

                                    | farmem, syscall, inkey,|

The editor forks the runtime once and talks to it over two pipes (PROTOCOL.md): commands go down, and text plus % events (%READY, %CERR, %DEBUG ...) come back. The program runs on its own terminal. The runtime forks the compiler at start-up and talks to it over two more pipes: LOAD, PACK, RUN's arguments and the debugger's statements go there, and compiled procedures (%PROC) and bound statements (%ICODE) come back; the compiler's own messages reach the editor directly. F1 forks the help browser on the editor's terminal and waits for it.

The address space

A Level 2 process sees 64K as eight 8K slots; the MMU maps any 8K block of physical RAM into any slot. Everything below competes for those eight.

7l2b09run code

l2b09run with a 40K workspace. Slot 7 is only good for 7,424 bytes on Wildbits ($FD00-$FFFF are fixed to I/O), so a module over 23,808 bytes cannot use it. Without the compiler l2b09run is 19,566 bytes, so its code can take slots 5-7; with a smaller workspace, a window (-b, far arrays) or the guard (L2GARD) takes the free slots.

  • Largest workspace: 40K with nothing else (it was 32K while the compiler was in the runtime); one 8K slot less for -b's code window, and one for far arrays' data window.
  • The workspace holds everything: the I-code of every loaded procedure, the variables of the running calls, the stacks and Basic09's tables. So a program's I-code must fit in somewhat less than the workspace, unless it is banked. The compiler keeps its own copy of every procedure in its own workspace, the same size as the runtime's (its code, 23,138 bytes, fits in slots 5-7 too).
  • Each module a program RUNs (WILD, farmem ...) and the overlay while it runs need a free slot too.
  • Getting slot 7 back needs l2b09run at or under 23,808 bytes and everything that must work at the largest workspace resident (the overlay needs a slot while it runs). A kernel change to keep F$MapBlk out of slot 7 was declined, as it interferes with another project. Done (2026-10-20): without the compiler, l2b09run is 19,566 bytes and a 40K workspace starts.

How far memory works

"Far" memory is RAM that is allocated but not mapped: blocks reserved with F$AllRAM, then mapped one at a time into a window slot with F$MapBlk and taken out with F$ClrBlk. A block change costs a couple of system calls (about 0.3-0.4 ms).

What is farHow it is usedWindow
farmem (P4)data, as recordsexplicit RUN farmem("alloc"/"put"/"get"/"free",...); must be freedone slot, held between calls
Far arrays (P7)array elementsDIM big(14000):FAR REAL, then normal syntax; blocks on first use, freed on returnthe data window
Banking (P6)procedure codenothing in the program: -b at startthe code window, one fixed slot

Far memory removes the limit on how much data or code a program can have, not on how much is visible at once: one 8K window per kind instead of the whole 64K.

Code banking (-b)

  1. At start-up -b=<kb> allocates a far store (today all of it at once) and reserves an 8K code window, the highest free slot.
  2. At load each procedure is compiled and bound as usual, then copied into the store; the workspace keeps a 34-byte stub (header, name, a banked flag, the block and offset). Small procedures are packed into blocks in load order.
  3. A call maps the callee's block into the window and runs it there; the return maps the caller's back. Within one block no cost; across blocks about 0.8 ms each way.
  4. The window never moves, because the runtime keeps pointers into running code; a remap that does not land in the same slot fails with 207.

Limits: 8K per procedure (7,424 if the window is slot 7); the store is never reused; PACK refuses banked procedures. make p6test loads about 48K of compiled code in a 24K workspace.

Ideas discussed

  • Allocate the store on demand, one block at a time: the stubs already hold absolute block numbers, so only the final free needs a table. -b=<kb> becomes a maximum. About 60-100 bytes.
  • Bank automatically: set up the window at the first load that runs out of workspace (nothing is running then), after Make's workspace growth has reached 24K; keep -b as an override.
  • Packed banked programs (runb-l2): PACK writes procedures as separate modules or one file; runb-l2 reads them into far RAM and runs them through the code window.

OS-9 Pascal compared

The Pascal in nitros9-languages is the original Pascal 2.0 as disassembled code, without comments or documentation, so this section is from general knowledge of OS-9 Pascal, not checked against its source.

OS-9 Pascal compiles to P-code, which an interpreter runs; the shell hands Prgrm+PCode modules to PascalS. The interpreters include PascalN, which loads the whole program into memory, and PascalS, which keeps the P-code on disk and reads procedures into a fixed buffer as they are called, replacing ones not used lately: virtual memory for code, done by the interpreter. PascalT translates P-code to native 6809 code.

For packed, banked Basic09 programs there are two matching routes:

  1. The PascalS route: runb-l2 opens the packed module as a file and reads a procedure's I-code into the window or a buffer when it is called. No far RAM, but slow calls to swapped-out code, especially from SD.
  2. Our route: at start-up runb-l2 reads the packed procedures from the file straight into far RAM, as L2BANK does after a load, and runs them through the code window as l2b09run does. The module never has to fit in the 64K.

On Level 2 with plenty of RAM, route 2 fits better: it reuses the tested L2RSLV/L2MAPW code. PascalS's model is the one to copy if Level 1, or a small-memory CoCo 3, ever matters.

The compiler, and a separate compiler process

How the compiler works

In stock Basic09 the compiler is part of the program; in basic09-l2 the same code runs in l2b09cc, a process of its own (Progress, below). LOAD reads the source a line at a time:

  1. compil (2,241 bytes) turns each line into I-code: keywords become tokens, constants become binary, names go into the procedure's symbol table. Line errors come back as %CERR.
  2. binder (3,589 bytes) runs at the end of each procedure: it lays out the variables, resolves line numbers, and checks what needs the whole procedure. Its errors come back as %BERR.
  3. The source is thrown away. LIST and SAVE decompile the I-code and symbol table; PACK strips the symbol table for RunB.

The compiler is also used while running: run p(args) compiles its arguments each time, and the debugger's PRINT, LET, Evaluate and watches compile statements against the paused procedure.

The design (built, 2026-10-20)

 basic09-l2 (editor) ==pipes==> l2b09run ==pipes==> l2b09cc
        (protocol unchanged)      (forks it on the first load)
  • Send the result, not the memory map. The compiler process compiles and binds in its own 64K and sends each finished procedure as a %PROC <bytes> frame; the runtime copies it into its workspace. A procedure's header holds offsets, not addresses, and calls to other procedures are linked at run time, so a bound procedure can be moved as bytes.
  • Sharing the runtime's map was rejected: Basic09's pointers are absolute, F$MapBlk cannot choose a slot, a child that exits with the runtime's blocks mapped can free them, and such a compiler would need a free slot in the runtime's map anyway, just as the overlay does.
  • The runtime forks it, so the editor protocol, l2b09ctl and the tests do not change. The runtime forwards the compiler's %CERR/%BERR lines.
  • What it frees: about 5.4K of l2b09run, enough for slot 7 and a 40K workspace, and room for GLOBAL storage, labels and MODULE.Procedure.
  • What has to move first: run arguments and the debugger's statements, which go to the compiler as small requests.
  • The first step is safe: receive procedures from the compiler while keeping the built-in compiler, and compare the two byte for byte.

  • 2026-10-20, RUN/STOP is a break: on hardware, RUN/STOP ended the program (or gave "Error 2 Keyboard Abort" at an INPUT), because the K2 sends it as the keyboard abort ($05, C$QUIT); ^C is the interrupt that stops in the debugger. l2b09run now treats the abort as a break, always, so either key stops the program in the debugger, and ^P ends it. This differs from stock Basic09, where a program's ON ERROR could trap error 2 from the keyboard. Images rebuilt (l2b09run 19,483, l2b09cc 24,342 bytes).
  • 2026-10-20, stepping keeps the editor's screen: F7 and F8 used to flash the program's screen at every step, and sometimes it stayed up, with the keyboard on it (F5 seemed dead; Alt+arrow helped): the switch to the program's terminal could come after the switch back, behind the program's output. Now a step keeps the editor's screen. l2b09run sends %INPUT as an INPUT is about to read the program's terminal, and only then does the editor show the program's screen, until it stops again. After a Run or Continue the editor switches back twice, 2 ticks apart. F5 still shows the program's screen at any time.
  • 2026-10-20, the stopped statement, not the line: on a line like PRINT \ PRINT \ PRINT the debugger stops at each statement, but the whole line was red. %DEBUG now carries a third number for the second and later statements on a line (from L2LINS, which counts them), and the editor paints only that statement red and puts the cursor at its start. A \ in a string is not a separator, and a statement starting with REM, (* or ! runs to the end of the line, as the compiler has it. make p5wtest steps along such a line and reads the colours off the screen. basic09-l2 23,182, l2b09run 19,566 bytes. A statement starting with ! is a comment too (added after the first build).
  • 2026-10-20, a hint for ":": most BASICs separate statements with :; Basic09 uses \, because : was taken by Pascal-style types (DIM k:INTEGER) and :=. PRINT 1 : PRINT 2 is stock error 31, "Missing DO". When the compiler's ^ points at such a :, the editor's message now reads Error 31 - use \ between statements, not :; the help page for error 31 says so too. The language is unchanged. make p5xtest; basic09-l2 23,306 bytes.
  • 2026-10-20, Shift+RUN/STOP is Run: the K2's RUN/STOP says "Run", but it is also the K2's only cancel key (it has no Esc; the driver sends $05 with or without Shift, and Shift is in SS.KySns). So in the editor Shift+RUN/STOP is Run, as ^R and as the Commodore load-and-run, and plain RUN/STOP still cancels; while a program runs both stop it in the debugger. Shift+Esc on a PS/2 keyboard. make p5ytest.
  • 2026-10-20, RUN/STOP at an INPUT: on hardware, RUN/STOP while startrek waited at INPUT "Command " still gave "Error 2 Keyboard Abort", and the first step then ended the program. A signal also ends the waiting terminal read, with the signal as its error code, and stock INPUT made only the interrupt (3) a debugger stop, after reporting it as an error. Now RUN/STOP and ^C at an INPUT both stop in the debugger as a plain break (no message), and Continue asks for the input again. make p8etest sends both signals through l2b09ctl to a program waiting on a real terminal.
  • 2026-10-20, the fork: src/ is basic09-l2's own source (tools/l2fork.py: 777 stock-only lines gone, every program byte-identical); no stock builds or make check any more, and p1 and p4 use the image's stock basic09 and runb.
  • 2026-10-20, the compiler's 32K cap lifted: l2b09cc's exprsn is assembled without the trig package, which a compiler never uses, so l2b09cc went from 24,425 to 22,842 bytes; its code can use slot 7, and it now gets the runtime's workspace, up to 40K (p8c loads startrek at #40k).

The full note is COMPILER.md.

Compatibility

Decided 2026-10-20, together with forking the source, which was done the same day: tools/l2fork.py turned Microware's source into basic09-l2's own, dropping the stock-only code (777 lines, the line editor among them), and every basic09-l2 program came out byte-identical. The stock builds and make check are gone; the rule is now:

  • Old programs must run on basic09-l2. Basic09 source files load, compile and run unchanged (the compiler is Microware's own code). PACKed I-Code modules, from stock Basic09 or built for stock RunB, run under l2b09run, by name and with arguments.
  • The other way is best effort. PACK output of a program that uses no new feature should still run under stock RunB. Programs using new features (far arrays, banking, and later GLOBAL, labels, MODULE.Procedure) may need basic09-l2; PACK refuses what stock RunB cannot run.
  • Tests: p4 (stock RunB runs our PACK output), p8a (stock behaviour of the debugger and RUN arguments, unchecked argument types included), p8d (a PACKed module run with arguments).

Compiler speed-ups (a log)

This section records how fast the compiler is, why, and each change made to it, with before and after measurements. Newest entries go at the end.

Why

  • The editor compiles whole procedures every time. Each Make sends every changed procedure to l2b09run as source. Stock Basic09 compiled one line at a time as you typed it in its line editor, so its slow parts went unnoticed.
  • The cost grew with the square of a procedure's length. Doubling a procedure tripled its compile time, so long procedures hurt most.
  • It is stock behaviour, from 1980: the same files gave the same times with l2b09run and stock basic09.

How it is measured

  • Time: in MAME (wbjr2), with the guest's clock (date -t before and after l2b09run loads a file), so the seconds are those of the real machine at 6.29 MHz. They include starting l2b09run (under a second).
  • Where the time goes: a MAME Lua read tap on l2b09run's code counts every byte the CPU reads from it, mapped to routines with the assembler listings. Reads are close to time spent.
  • Test files: startrek (937 lines in 8 procedures, 20.7K of source); one procedure of 800 lines a=a+1 (u800); the same with line numbers (n800); 8 procedures of 100 numbered lines (m800).

  1. The binder patched the procedure one token at a time. When types are mixed (in a=a+1, a is REAL and 1 an integer), it inserts a conversion token (INSTOK, binder.asm). Each insertion went through REPLAC to FLOTUP, which moves the rest of the procedure up by rotating it in place, a byte at a time, at about 60 cycles a byte. One insertion per statement made binding quadratic. The design needs no buffer, which mattered in 1980.
  2. REPLAC then copied the rest of the procedure onto itself. Its "delete" step moved everything above the insertion down by the number of bytes deleted, even when that number was zero.
  3. Each numbered line searched the procedure from the start (SCHLIN), statement by statement, to find where it belonged or which line it replaced. The line editor needed that, because 150 PRINT x could be typed at any time. A file loaded from top to bottom does not.

2026-10-20: change 1, faster inserts and no needless searches

  • L2FLUP (src/editor): when an insertion is 8 bytes or fewer (the binder's are 1), keep the new bytes on the stack, block-move the I-code above up with MOVUP (4 bytes a loop, about 9 cycles a byte), and put the bytes in the gap. Longer insertions still use FLOTUP.
  • REPLAC skips the "delete" copy when nothing was deleted.
  • INSERT: a numbered line above every line so far goes straight to the end, without the two searches. The highest number so far is kept in the new procedure's P.EXEC, which is 0 for a new procedure and which the binder clears before using. A lower or repeated number still takes the old path, so out-of-order files load as before.
  • Cost: 93 bytes of l2b09run (23,852 → 23,945). All three changes are behind ifne L2B09, and stock builds stay byte-identical.
  • Checked: the old and new runtimes PACK byte-identical modules for startrek, u800, n800, m800, a file with out-of-order and repeated line numbers, and one with many conversions (fix, float, subscripts). All the emulator tests pass.

What is left (startrek, 29.6M reads instead of 96.5M): the keyword and name searches (SEARC* in compil) are now about 60%, and the block moves about 18%. The searches are linear. An index or a hash would cut them, but that costs more bytes than l2b09run has to spare, so it belongs in the separate compiler (COMPILER.md), as does a binder that adds its tokens in one pass.

2026-10-20: change 2, the keyword table indexed (in l2b09cc)

  • Why: every name in the source was looked up in the keyword table (115 entries, one after another) before the procedure's own names. l2b09cc on its own, profiled loading startrek: 33.6M reads, the table searches 52% of them.
  • What: tools/kwsort.py sorts KEYTAB by name (each entry carries its token, and the decompiler finds entries by token, so the order does not matter) and generates KWIDX, a first-letter index (offset and count for A-Z, 78 bytes), in l2b09cc only. KWSRCH in compil searches only the name's first letter's keywords.
  • Result: 25.1M reads, a quarter less; the searches are 37% now, mostly the procedure's own names (a growing table, not sorted). Loading startrek with l2b09cc alone takes about 3 s either way at one-second resolution.
  • Checked: stock Basic09 (the image's own basic09) and l2b09cc PACK startrek into byte-identical modules, now part of make p8dtest. Comparing the compiler's %PROC frames before and after found one difference, 2 bytes in startrek's description area that hold a value depending on where the compiler's code sits: stock Basic09 does the same, PACK writes the field the same way in both, so it does not matter, but it means bound procedures are compared after PACK, not before.

2026-10-20: change 3, the procedure's names indexed (in l2b09cc)

  • Why: a name that is not a keyword is then looked up among the procedure's own names, again one after another, comparing each a character at a time.
  • What: the symbol table only grows at its end, and moves as a whole, so its entries keep their offsets. ADDSYM now also writes each name's offset and first letter into a fixed-size index (3 bytes a name, up to 255, below the breakpoint table in l2b09cc's workspace), and SYMSRC compares only the names with the right first letter. It is used only while it is the compiling procedure's and has as many names as its table; otherwise, as for a debugger statement against a stored procedure, the plain search runs. The first-letter test of change 2 also missed one-letter names (I, X), whose letter carries the end-of-name bit, so they took the full keyword search; fixed.
  • Result: 21.7M reads for startrek (25.1M after change 2, 33.6M before it), and about 2 s instead of 3 for l2b09cc alone. l2b09cc 23,138 bytes. The PACK comparison with stock Basic09 still matches.
  • A caution about the profile: the read tap counts every read in l2b09cc's address range, also those made in system state, where other code sits at those addresses; per-routine counts high in the module are not to be trusted (a routine that never ran showed 2,107 calls). Totals compare fine between runs.
  • What is left: the binder's block moves for its inserted tokens (MOVUP), and the I-Code moves of compiling at all. Rather than more of these, a binder that builds the procedure in one pass (COMPILER.md, step 5) is the next real gain.
